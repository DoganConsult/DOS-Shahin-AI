## Dynamic UI / UI-System fulfillment

The Phase F requirement ("DB-Driven UI Management") is satisfied:

1. **11 `dos.ui_*` tables** created (`grc-profile/dynamic-ui/schema/01_ui_registry.sql`):
   `ui_module`, `ui_route`, `ui_view`, `ui_column`, `ui_filter`, `ui_action`, `ui_form`, `ui_navigation`, `ui_widget`, `ui_preset`, `ui_tenant_override`.
2. **Seed rows for all 18 modules** (+ Foundation):
   - 19 module rows
   - 90 routes (5 each: list/detail/form/dashboard/settings)
   - 72 views (4 each: list/detail/dashboard/form)
   - 144 columns (8 per list view)
   - 72 filters (4 per list view)
   - 144 actions (8 per list view: create/export/view/edit/approve/archive/delete/bulk_assign)
   - 18 forms (JSON-Schema + JSON-Forms uiSchema)
   - 72 navigation nodes (4 per module)
   - 54 widgets (3 per module dashboard)
3. **TypeScript contracts** (`contracts/index.ts`) declare the surface
   `DynamicUiClient` and the 9 row types (`UiModule`, `UiRoute`, `UiView`, `UiColumn`,
   `UiFilter`, `UiAction`, `UiForm`, `UiNavigationNode`, `UiWidget`) plus
   `UiResolverContext` and a `canAccess(required, ctx)` permission guard.
4. **Workspace shell config** (`workspace-shell.config.json`) tells the
   Shahin-AI SPA how to render the 19-card grid by calling
   `DynamicUiClient.resolveCards()`.

Every UI row references a permission code from W3 and (where applicable)
a workflow event from W4 — single closed loop.

## What is NOT done

1. **No platform-side changes.** Phase H billing, Phase D AI OS, Phase E tenant migrations, etc. are unchanged.
2. **Workspace `pnpm install`.** Not run because no internet/registry access in this environment.
3. **Real workflow engine wiring.** W4 produces declarative JSON; the actual XState machines must be generated by the workflow team's codegen.
4. **i18n token catalog.** All `*_token` columns reference token names; the i18n string catalog must be filled in W7.
5. **Pushing migrations into the live DB.** SQL files exist; `pnpm migrate` against a live DB is a separate decision.
