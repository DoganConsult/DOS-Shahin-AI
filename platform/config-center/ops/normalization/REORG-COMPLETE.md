
`modules/platform-core/db/` additionally has `_frozen/` which preserves the
4 multi-owner tenant-baseline files plus the combo-service source files —
the migration runner discovers them for fresh-DB apply, and their
per-module **shards** (85 total, written with `-- dos:supersedes-checksum:`
headers) are skipped via supersedes-provenance on subsequent runs.

## Migration runner changes (additive)

[migration/migration-runner.ts](migration/migration-runner.ts):

1. **Schema**: `dos.platform_migrations.current_path TEXT` nullable column
   — added by [modules/platform-core/db/public/migrations/20260422_0001_platform_migrations_current_path.sql](modules/platform-core/db/public/migrations/20260422_0001_platform_migrations_current_path.sql).
2. **Discovery**: `discoverAllMigrations()` walks `ops/migrations`, `migration`,
   every `modules/*/db/{tenant,public}/migrations`, every
   `services/*/migrations`, and every legacy `modules/*/source/backend/*/migrations`.
   Stable ordering by filename, then path — preserves the historical apply
   sequence.
3. **Checksum remap**: when a file's filename is not in `dos.platform_migrations`
   but its SHA-256 matches an applied row, the runner updates `current_path`
   and treats as applied — enabling safe git-mv of applied files.
4. **Supersedes provenance**: shards stamped with
   `-- dos:supersedes-checksum: <sha256>` are treated as applied whenever
   the parent checksum is in the migrations ledger, without re-executing
   DDL.
5. **CLI default**: `ts-node migration-runner.ts up` (no `--dir`) now runs
   multi-root discovery. Passing `--dir <path>` preserves legacy single-dir
   behavior.

## Ownership enforcement

The source of truth for "which module owns which table" is
[ops/normalization/module-prefixes.yml](ops/normalization/module-prefixes.yml).
Each entry has: `primary` prefixes, `explicit_prefix` (compound like
`governance_ai`), `explicit` exact-match table names, and
`explicit_exclude` to carve platform-core tables out of module scope
(e.g. `audit_trail` belongs to platform-core, not audit).

`file_overrides` handles single-owner files whose table contents would
miscount (platform rename ops, drift-repair ALTERs targeting dos.*).
Four values allowed: a module name, `SPLIT`, `EXCLUDE`, or any module name.

CI guard — `make -C ops/normalization ownership-check`:
- Freeze enforcement: no new files under `ops/migrations/` or `migration/`
- Legacy drain: no files under `modules/*/source/backend/*/migrations/`
- Header mismatch: a shard stamped `-- dos:owning-module: X` must live
  under `modules/X/db/`
- Cross-owner DDL (warning only): a module's migration touching a
  neighbor's tables

## Pipeline (repeatable, read-only)

```
make -C ops/normalization catalog           # scan catalog.yml across full tree
npx tsx ops/normalization/scripts/file-to-table.ts           # reverse index
npx tsx ops/normalization/scripts/classify-by-prefix.ts      # classification
npx tsx ops/normalization/scripts/classify-leftovers.ts      # content-aware fallback
make -C ops/normalization manifests         # regenerate per-module manifest.yml
make -C ops/normalization ownership-check   # CI guard (exit 1 on violation)
make -C ops/normalization module-report MODULE=<name>   # per-module scorecard
```

## Splitter provenance

4 mega-baselines + 7 combo-service migrations were split into 85 per-module
shards via [ops/normalization/scripts/split-megafile.ts](ops/normalization/scripts/split-megafile.ts).
Each shard carries these header lines:

```
-- dos:extracted-from: <source path>
-- dos:supersedes-checksum: <SHA-256 of source>
-- dos:owning-module: <module>
-- dos:tables: <comma-separated tables>
-- dos:statement-count: <N>
```

The sources themselves are in `modules/platform-core/db/_frozen/` preserving
their original relative path for provenance — still runner-discoverable so
fresh databases apply them once; per-module shards register as applied via
the supersedes handshake, no DDL re-execution.

## Per-module normalization kickoff

The normalization toolkit at [ops/normalization/](ops/normalization/)
(Makefile with 60 targets: fk-plan, jsonb-plan, nf1/nf3/dknf-plan, grade)
already operates on the full catalog — it picks up the new per-module
layout without changes, because it reads `catalog.yml` which now indexes
every location.

To drive normalization per module:

```
make -C ops/normalization module-report MODULE=<name>
# then, on proposals the module owner accepts:
make -C ops/normalization fk-plan jsonb-plan nf3-plan dknf-plan
# accepted proposals emit migrations into modules/<name>/db/tenant/migrations/
```
