# DB Normalization Framework — 6 Grades

A practical scoring system for every table in the platform.
Six normal forms are evaluated per table; the table's overall **grade**
is the highest form it satisfies. Per-table results live in
[normalization-scorecard.md](normalization-scorecard.md), generated by
[scripts/normalize-grade.ts](scripts/normalize-grade.ts).

This is a static-analysis grader. It cannot see runtime data. Where a
form genuinely requires functional-dependency analysis (2NF, BCNF), the
grader emits a **REVIEW** verdict instead of a pass/fail; the operator
finalizes by reading the table's queries and call-sites.

---

## The six grades

### 1NF — atomic, no repeating groups

**Definition (textbook):** every column holds an atomic value; no
repeating groups; rows are uniquely identifiable.

**This codebase:**
- ✗ Any `TEXT[]`, `JSONB[]`, `INT[]` column where the array elements
  represent *first-class entities* with their own identity (e.g.
  `frameworks TEXT[]` on `controls`, `roles JSONB` on `raci_matrices`)
  → 1NF violation. The array elements should be rows in a child table
  with an FK back.
- ✗ Repeating-group columns (`field_1`, `field_2`, `field_3`) → 1NF
  violation.
- ✗ JSONB used as an unstructured "bag of fields" with stable shape
  (≥80% top-key overlap across rows) → 1NF violation; the bag should
  be promoted to typed columns or a child table. Existing planner:
  [scripts/jsonb-decompose-plan.ts](scripts/jsonb-decompose-plan.ts).
- ✓ Arrays where order is the only thing that matters (e.g.
  `tags TEXT[]` for free-form labels) — acceptable for 1NF.
- ✓ JSONB used for genuinely document-shaped data (settings,
  preferences, audit payloads) — acceptable.

**Auto-detect signals:** `*_array_columns`, `*_repeating_columns`,
`*_jsonb_stable_shape` (when sampled).

### 2NF — full functional dependence on the primary key

**Definition:** non-key attributes depend on the *whole* PK, not a
subset.

**Only matters when the PK is composite.** Single-column PKs (the vast
majority in this codebase, since most tables use `id UUID`) are
trivially in 2NF.

**This codebase:**
- ✗ Composite PK `(tenant_id, x_id)` with a column `x_name` that depends
  only on `x_id` → 2NF violation; `x_name` belongs in the parent of
  `x_id`.
- The grader can detect: composite PK exists → emit **REVIEW** with a
  list of non-key columns to inspect for partial dependency.

**Auto-detect signals:** `composite_pk_with_non_key_columns`.

### 3NF — no transitive dependencies

**Definition:** non-key attribute does not depend on another non-key
attribute.

**This codebase — concrete patterns:**
- ✗ `<entity>_id` + `<entity>_name` / `<entity>_label` / `<entity>_code`
  in the same row → the name/label/code is determined by the id, which
  is itself determined by the row's PK. The name belongs in the parent
  table; this row should hold only the FK.
  Example: `controls.framework_id` + `controls.framework_name` →
  `framework_name` should come from `frameworks` via JOIN.
- ✗ Denormalized counters (`<x>_count` integer columns) — the count
  is derivable from a child table; storing it creates drift risk.
  Existing planner: [scripts/counter-cleanup-plan.ts](scripts/counter-cleanup-plan.ts).
- ✓ Snapshot/historical fields (`amount_at_creation`, `currency_at_event`)
  — intentionally denormalized for audit purposes; not 3NF violations
  in spirit.

**Auto-detect signals:** `transitive_id_name_pair`, `denorm_counter`,
`computed_column_stored`.

### BCNF — every determinant is a candidate key

**Definition:** for every non-trivial functional dependency X → Y,
X is a superkey.

**Strict BCNF requires functional-dependency analysis.** The grader
emits **REVIEW** for tables that have:
- Multiple `UNIQUE` constraints on different column subsets
- Composite PK with a UNIQUE constraint on a different subset

That's the operator's signal that a non-PK candidate key exists and
the schema needs review for BCNF compliance.

**Auto-detect signals:** `multiple_alternate_keys`,
`composite_pk_plus_alternate_unique`.

### 4NF — no multivalued dependencies

**Definition:** for every multivalued dependency X →→ Y, X is a
superkey. Concretely: a row should not encode two independent
many-to-many relationships.

**This codebase — concrete patterns:**
- ✗ A row with two independent JSONB arrays (e.g.
  `team_raci_assignments.modules JSONB DEFAULT '[]'` AND
  `team_raci_assignments.dashboard_widgets JSONB DEFAULT '[]'`) — two
  unrelated lists in one row. 4NF demands they live in separate child
  tables, each tying back to the row's PK.
- ✗ A row with two independent `TEXT[]` columns covering different
  domains.
- ✓ A row with one array column or one JSONB plus scalar fields —
  fine for 4NF (1NF still applies).

**Auto-detect signals:** `multiple_independent_arrays_or_jsonb`.

### DKNF — domain-key normal form

**Definition:** every constraint can be expressed as the consequence
of domain constraints + key constraints.

**This codebase — concrete patterns:**
- ✗ `CHECK (col IN ('A','B','C'))` on a TEXT column — the constraint is
  expressible only in DDL, not as a domain. Promote to a Postgres
  `ENUM` type or a lookup table with FK so the value set is part of
  the type system.
- ✗ Free-text column with documented allowed values in a comment but no
  CHECK — implicit domain not enforced.
- ✓ Columns typed as proper enums or referencing FK lookup tables —
  DKNF-clean.

**Auto-detect signals:** `check_in_list_on_text`, `free_text_with_documented_enum`.

## Grade output

Per table, the grader writes a row to `normalization-scorecard.md`:

```
| table | grade | 1NF | 2NF | 3NF | BCNF | 4NF | DKNF | top-violation |
|---|---|---|---|---|---|---|---|---|
| controls | 1NF | ✗ frameworks-text-array; ✗ framework_id+framework_name | ✓ | ✗ | REVIEW | ✓ | ✓ | promote frameworks to controls_frameworks(control_id, framework_id) |
```

- **✓ pass** — auto-checks find no violation
- **✗ fail** — concrete violation surfaced (with the specific column)
- **REVIEW** — needs functional-dependency analysis the grader can't do
- **N/A** — not applicable (e.g. 2NF on a single-PK table)

The **grade** column is the *highest form satisfied* — i.e. if 1NF fails,
the table is graded "below 1NF" (= UNGRADED). If 1NF passes but 3NF fails,
the grade is 2NF. The summary at the top of the scorecard reports the
distribution.

## Grading rollup

The scorecard's summary block reports:

```
Total tables:                     2,152
Reaching DKNF:                       12
Reaching 4NF:                        87
Reaching BCNF (incl. REVIEW):       430
Reaching 3NF:                     1,018
Reaching 2NF:                     1,540
Reaching 1NF:                     1,890
Below 1NF (ungraded):               262
```

This is the **maturity ladder**. The platform's overall grade is the
median table grade, weighted by row volume in production (which the
grader can't see; the operator weights manually).

## How to use the grader

```
make catalog              # rebuild source-of-truth catalog
make grade                # produce normalization-scorecard.md
make normalize            # grade + per-form fix planners (1NF, 3NF, DKNF)
```

The grader is read-only against the file system. It never touches the
DB. Per-form fix planners emit decision matrices + commented-out SQL
templates (the operator uncomments per table after review) — same
discipline as `fk-rebuild-emit.ts`.

## How to act on a grade

1. **Below 1NF (ungraded)** — top priority. The table is structurally
   incorrect; fix 1NF first, everything else cascades.
2. **1NF pass, 3NF fail** — second priority; almost always an extracted
   denormalization pattern. Use `scripts/3nf-fix-plan.ts` to generate
   fix scaffolds.
3. **REVIEW grades (BCNF, 2NF)** — schedule operator review.
4. **DKNF fail** — usually a quick CHECK→ENUM migration; use
   `scripts/dknf-fix-plan.ts`.
5. **4NF fail** — typically requires schema redesign + data migration;
   plan as a multi-pass effort.

## Hard rules

- The grader is a **diagnostic**, not a fix. Every emitted scaffold
  must be reviewed before applying.
- A table with a passing grade today can regress; CI gate
  (`db-normalization.yml`) reads `drift-baseline.json` and fails any
  PR that drops the grade of any table.
- The grader does not consider RLS, indexes, or performance — those
  live in separate review systems.
- The grader does not score views or matviews; only base tables.
